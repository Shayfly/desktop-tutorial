Claude — הרחבת מפרט Agent OS ו־Skills Runtime של 148AI

המסמך הזה משלים את הוראת הביצוע הקודמת. שלב אותו בתוכנית הקיימת ושמור את העבודה שכבר בוצעה.

**המטרה**

148AI צריכה להיות מערכת שמסוגלת לתכנן, לבנות, לבדוק, לתקן ולהפעיל מוצרים באמצעות אג׳נטים וסקילים מפורשים.

משפחות המוצרים: אתרים ואפליקציות ווב, מערכות עסקיות, משחקים, תמונות ונכסים, וידאו ואודיו, סוכני AI ואוטומציות. מובייל ומוצרי Desktop יתווספו באמצעות מסלולי ביצוע מתאימים.

יש להבחין בכל עת בין:

- יכולת שהוגדרה.
- יכולת שמומשה.
- יכולת שחוברה לספק ולסביבת הרצה.
- יכולת שאומתה בפועל.
- יכולת שחסומה בגלל חיבור, הרשאה או תשתית.

אל תציג תמיכה במשפחת מוצר רק משום שקיים עבורה אג׳נט או prompt.

**1. כללים משותפים לכל האג׳נטים**

כל אג׳נט חייב לקבל הגדרה מפורשת של אחריות, קלט ופלט, Skills מותרים, פעולות אסורות, הרשאות, תקציב, ספקים, מצב עמיד, retries, הסלמה, תנאי הצלחה ובדיקות.

אג׳נט צריך לפעול רק כשיש צורך בתפקידו. אין להפעיל את כל האג׳נטים בכל בקשה.

ניתן לממש כמה תפקידים באותו worker או שירות. ריבוי שמות אינו מחייב ריבוי תהליכים או קריאות מודל.

פעולות דטרמיניסטיות — חישוב עלויות, בדיקת הרשאות, אימות schemas, חישוב hashes ותיאום locks — יבוצעו בקוד רגיל.

לכל שינוי בקבצים, נתונים או שירות חיצוני חייבים להיות בעלות ברורה, תיעוד ואופן טיפול בכשל.

**10. חוזה משותף לכל Skill**

כל Skill צריך להגדיר:

- מטרה וגבולות.
- schema של קלט ופלט.
- תנאים מוקדמים ותלויות.
- כלים וספקים מותרים.
- תופעות לוואי אפשריות.
- תקציב, timeout ו־retry policy.
- idempotency כשנדרשת.
- דרך ביטול, cleanup או compensation.
- הצלחה, כשל וחוסר ודאות.
- בדיקות וראיות.

הבדל בין כשל שניתן לנסות שוב לבין כשל שמחייב שינוי קלט, הרשאה או התערבות.

אל תבצע retry אוטומטי על פעולה חיצונית שעלולה כבר להתבצע בלי לבדוק את מצבה.

**11. זיכרון, מצב וגרסאות**

הפרד בין:

- מצב המשימה הנוכחית.
- עובדות והחלטות של הפרויקט.
- העדפות משתמש מאושרות.
- תוצרים וקבצים.
- ניסיון ביצוע ולוגים.

אין להפוך השערה של מודל לעובדה קבועה.

קשר כל ביצוע לגרסת הקוד, האג׳נט, הסקיל והמחירון. אפשר לדעת בדיעבד מה בדיוק הופעל.

שמור checkpoint לפני פעולות ארוכות. התאוששות צריכה להמשיך מהשלב המתאים ולא להתחיל מחדש פעולה שכבר הצליחה.

**12. הפרדת פרויקטים והרשאות**

כל קריאת נתונים, קובץ, זיכרון וסוד חייבת להיות קשורה למשתמש ולפרויקט הנכונים.

ממש גישה לסודות דרך מנגנון ה־Vault הקיים. אל תשלח סודות לפרומפטים ללא צורך ואל תשמור אותם בתוצרי הלקוח.

הבחן בין שלושת מודלי החיבור:

- `MANAGED_BY_148AI`
- `CUSTOMER_CONNECTED`
- `BYOK`

הבחירה משפיעה על בעלות, עלות, הרשאות, ביטול חיבור ותמיכה. אל תחליף מודל חיבור בשקט.

**13. ניתוב ספקים וחיסכון**

בנה ניתוב לפי התאמה למשימה, איכות מוכחת, עלות, זמינות והרשאות נתונים.

מסלול חינמי יכול להיבחר כשמתאים, אבל לא רק משום שהוא חינמי.

ממש:

- מודל זול למשימות פשוטות כשהוא עומד בבדיקות.
- מודל חזק להסלמה ממוקדת.
- context ממוקד בקבצים הרלוונטיים.
- caching כשמתאים.
- הגבלת ניסיונות תיקון.
- מניעת עבודה כפולה.
- חישוב עלות לכל שלב ולכל מוצר.

הערכת מחיר אינה חיוב מאומת. שימור התקציב וההתאמה מול הספק חייבים להישאר פעילים גם בעת fallback.

**14. חוקיות ומקור נכסים**

שלב את מדיניות ה־IP הקיימת: הצהרות משתמש, הבחנה בין שימוש אישי למסחרי, תיעוד הסכמה ומקור נכסים, ואפשרות חסימה או טיפול בתלונה.

בדיקות אוטומטיות יכולות לזהות ולסמן סיכון; הן אינן אישור משפטי לשימוש.

אל תמציא רישיון לנכס או זכות מסחרית לספק.

**15. Universal Live Workspace**

שמור ממשק עבודה משותף, עם Preview Adapter לפי משפחת המוצר:

| יעד | מה ניתן לבדוק |
|---|---|
| Web | דפדפן, ניווט, טפסים ו־API |
| Game | התחלה, קלט, משחקיות ושמירה |
| API | בקשות, responses והרשאות |
| Agent | משימות, כלים, זיכרון ותוצאות |
| Automation | טריגר, רצף פעולות וכשלים |
| Media | ניגון, timeline, קול וכתוביות |
| Mobile | תצוגה והרצה מתאימות לפלטפורמה כשהתשתית זמינה |

תצוגת Web אינה הוכחה לאפליקציית מובייל native.

המשתמש צריך לראות תוצרים, גרסאות, התקדמות, עלויות וראיות אימות באותו מרחב עבודה.

**16. סדר הביצוע**

היקף הרישום כולל את כל המשפחות. היקף המימוש מתקדם לפי שערי אימות:

1. מיפוי הקיים ותיקון חוסר התאמה ב־Registries.
2. Runtime, הרשאות, מצב עמיד ובקרת עלויות.
3. מסלול ווב מלא ומאומת.
4. יצירה ושילוב של תמונה אמיתית באותו מוצר.
5. משחק קטן עם משחקיות ושמירה.
6. אוטומציה אחת עם חיבור מורשה.
7. סוכן AI אחד שנוצר ללקוח.
8. מסלול מדיה קצר עם יצירה, הרכבה וניגון.
9. הרחבות מורכבות, מובייל ומולטיפלייר בהתאם לתשתיות.

אין צורך לממש מראש כל תפקיד כתהליך נפרד. יש צורך לשמור חוזים מפורשים ובעלות ברורה על כל משימה.

**17. בדיקות רוחב נדרשות**

בדוק לפחות:

- ניסיון להפעיל Skill שאינו מורשה.
- תלות חסרה או ספק לא מחובר.
- שתי משימות מקבילות על אותו פרויקט.
- מסירה כפולה ולחיצה כפולה.
- רענון דף וקריסת worker.
- timeout עם מצב פעולה לא ידוע.
- כשל ספק ומעבר לספק חלופי.
- נתוני שימוש חסרים.
- תקציב שלא מספיק להרצה.
- חוסר גישה לפרויקט של משתמש אחר.
- שמירת תוצרים וגרסאות.
- חזרה לגרסה קודמת.
- תוצר שעבר compilation אך נכשל בתהליך המשתמש.

Mock tests בודקים את ההתנהגות הפנימית. עבור יכולות חיצוניות נדרשת גם ראיית ביצוע אמיתית, במסגרת התקציב המאושר.

**18. תנאי מסירה**

בסיום כל שלב הצג טבלה:

`Agent/Skill | Implementation | Configuration | Verification | Evidence | Cost | Remaining gap`

צרף קומיט, בדיקות, קישור Preview כשקיים וחסמים מדויקים.

רשום יכולות עתידיות בסטטוס אמיתי. אל תסמן אותן כזמינות בממשק רק משום שהוגדרו במסמך.

התקציב המאושר נשאר 10 דולר בסך הכול. אל תנסה להשלים את כל מסלולי הספקים בתוכו באמצעות הכרזות ללא בדיקה. השלם עבודה מקומית שאפשר לבדוק, ותעד אילו בדיקות אמיתיות נותרו ומה העלות המשוערת שלהן.

היעד הוא מערכת אחת: בקשה → תכנון → ביצוע → בדיקה → תיקון → אימות → תוצר → תצוגה או פרסום, עם אחריות, הרשאות, מצב ועלויות שניתן להסביר.
