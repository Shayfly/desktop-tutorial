# System map

The state mapping of the system map (the owner's plan v3, S1.5). Generated by `python -m omni_prod.system_map --write` from `omni_prod/system_map.py` alone. Do not edit by hand: `tests/test_system_map.py` fails when this file differs from what the code gives.

## Where the full map is

The full map -- every agent, role, skill and model with its state, and the inventory (endpoints, tables and migrations, worker services, queues, workflows, environment variable names, package dependencies, known limitations) -- is not committed. It changes with almost every pull request, and a committed copy goes stale on main whenever a branch cut before it, or two green pull requests that each regenerated it, merge: the required jobs test the head of a pull request, not the merge (the review of #532, 2026-11-25; CLAUDE.md section 4).

- **In CI**, on every push to main and every pull request: the job `light` of `v24-ci` builds it, keeps it as the artifact `system-map` (`SYSTEM_MAP.json`) of the run, and writes a summary table into the run's summary. A failure of the generator fails that step; `light` is not a required check.
- **Locally:** `python -m omni_prod.system_map --write` writes it to `SYSTEM_MAP.json` at the root of the repository, which git ignores; `python -m omni_prod.system_map --json PATH` writes it anywhere.

## States

The plan's six states: NOT_IMPLEMENTED, PARTIAL, IMPLEMENTED, CONNECTED, VERIFIED, LIVE.

LIVE is never derived here: it needs evidence younger than 7 days on the SHA that is deployed, and that evidence is in GitHub Actions runs and Vercel deployments, not in the repository.

### How a source word becomes a state

| Source word | State |
|---|---|
| DEFINED | NOT_IMPLEMENTED |
| NOT_IMPLEMENTED | NOT_IMPLEMENTED |
| IMPLEMENTED | IMPLEMENTED |
| TESTED | IMPLEMENTED |
| CONNECTED | CONNECTED |
| VERIFIED | VERIFIED |
| STALE | IMPLEMENTED |
| BLOCKED | PARTIAL |
| UNIT_TESTED | IMPLEMENTED |
| INTEGRATION_TESTED | IMPLEMENTED |
| REAL_SERVER_VERIFIED | VERIFIED |
| LIVE | VERIFIED |
| REAL_EXECUTION_VERIFIED | VERIFIED |
| CONNECTION_TESTED | CONNECTED |
| INSUFFICIENT_CREDIT | PARTIAL |
| CREDIT_EXHAUSTED | PARTIAL |

A word that is not in this table raises: a new status in a source is classified by a person, never guessed.

Rules beyond the table. OWNERS.md rule 7 records the owner's approval of the mapping on the evening of 2026-11-25, given as a general approval ("מאשר לך הכול"). The rules marked "added later" and the words INSUFFICIENT_CREDIT, CREDIT_EXHAUSTED were added after that by the review of #532; they rest on his standing approval (OWNERS.md rule 1):

- STALE -> IMPLEMENTED: it was verified once and its code changed since, so the evidence no longer covers it.
- TESTED, UNIT_TESTED, INTEGRATION_TESTED -> IMPLEMENTED: a test is not an execution check on a real server.
- BLOCKED, INSUFFICIENT_CREDIT, CREDIT_EXHAUSTED -> PARTIAL, or NOT_IMPLEMENTED when no code is named: code exists but a named dependency stops it.
- a gap or missing contract fields turn IMPLEMENTED or CONNECTED into PARTIAL: the plan: PARTIAL follows the component's gap list.
- LIVE in a source -> VERIFIED here: LIVE needs evidence on the deployed SHA younger than 7 days, which the repository does not hold.
- CREDENTIAL_PRESENT alone is not CONNECTED: a key that was never used to call the provider proves no connection.
- a model that is BLOCKED, has a blocking health (CREDIT_EXHAUSTED ...) or is INSUFFICIENT_CREDIT takes that word, before CONNECTION_TESTED and REAL_EXECUTION_VERIFIED: a model that cannot take work is neither connected nor verified, whatever answered before (PROVIDER_MATRIX ranks BLOCKED above IMPLEMENTED; intelligence/states.py: a route in a blocking health takes no work). (added later)
- a role that registry_audit calls CONNECTED with unit tests only (no configuration) is read as UNIT_TESTED: registry_audit gives CONNECTED for "configuration observed or unit tests only"; a unit test is not a connection. (added later)

## How the inventory is read

- Endpoints: the route decorators of every omni_prod module, with the prefix of their `APIRouter` and of an `include_router(..., prefix=...)`; a prefix the map cannot read raises.
- Database: `CREATE TABLE` in `infra/postgres/<number>_*.sql`; down files in `infra/postgres/rollback/`.
- Queues: the queue names in `omni_prod/queueing.py` and `omni_prod/intake/reservation_worker.py`; a name ending in `-` is a prefix of per-host queues and is listed apart, never as a queue.
- Environment variable names (names only, never values): names read with os.environ.get / os.getenv / os.environ[...] / `in os.environ`, or through an env mapping (env, environ, self.env, self._env), with a string literal, a module or class constant, a constant imported from another omni_prod module, or a loop over such names; and the names passed to a package helper whose parameter reaches such a read (found from the code, listed in `helpers`). A name built at run time (an f-string, a concatenation) is not found: those reads are counted in `unresolved`.
- Agents, roles, skills and models: `AGENT_OS_REGISTRY.json`, `omni_prod.registry_audit`, `PROVIDER_MATRIX.json`, through the table above.
